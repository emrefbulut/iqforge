## iqforge v0.4.0

`0.3.0` shipped `iqforge audit`. This release is what happened when that command
was pointed at eight public RF datasets instead of at the repository's own
fixtures: it found four bugs in itself, one correctness bug in `build` that had
been shipping since `0.1.0`, and one dataset it could not rule out.

### Correctness: check datasets built from a CSV

`--labels csv` and `--group-by csv:` matched recordings by **file name** rather
than by path. In a nested layout the same name repeats under every directory, so
rows for different recordings collided and the last one won. On a public LoRa
capture set — where `3.sigmf-meta` exists under every session and every receiver
— a 312-row label table collapsed to 47 distinct keys and **310 of 312
recordings came out carrying one label**.

Nothing warned. Every recording was labelled, the class counts looked plausible,
and the split satisfied every constraint the tool checks. It was a valid dataset
of confidently wrong labels, which is exactly the outcome the annotation path
documents refusing to produce.

**Affects `0.1.0`, `0.2.0` and `0.3.0`.** A flat directory of uniquely named
recordings is unaffected — which is why the repository's own fixtures, all flat
and uniquely named, could never have caught it.

```bash
iqforge audit <dataset-or-folder>
```

Both paths now match the value as written, falling back to the bare name only
when it is unambiguous and refusing with a message naming the fix when it is
not. `build --labels csv` additionally **errors** when the labels the CSV
declares do not all survive into the dataset. There is no threshold on class
imbalance anywhere in this: a rare-event dataset with 200 background against 1
event passes silently, because imbalance is a normal thing to want and a warning
that fires on a whole legitimate category stops being read.

### `audit` after eight datasets

Pointing the command at real data broke it in four ways, each fixed and each
with a regression test:

- **`core:datetime` was read from `global`.** SigMF puts it in `captures`, so
  the capture-time confound check reported NOT CHECKED on every conforming
  recording — while hiding, on a public jamming dataset, that the two classes
  were recorded a week apart and capture time alone classifies 100% of them.
- **Class axes were ranked by raw score.** An axis measurable on only one class
  scores 100% against a chance of 100%, and was reported as the reason a task
  sits at the ceiling: right verdict, wrong reason. Axes rank by margin over
  chance now.
- **A constant timestamp read as simultaneity.** `examples/` stamps all 16
  recordings `2024-01-01T00:00:00Z`; taken literally that is sixteen
  simultaneous captures, and the new air-time check called it a leak on the
  project's own example data.
- **One unreadable file aborted the whole folder.** A single `cf16_le` recording
  in a 330-file set produced no report at all.

New in the command:

- **`--labels csv`** with `--label-file`, so a CSV-labelled dataset can be
  assessed before it is built — which is the point of auditing a folder.
- **`shared air time`**: recordings whose capture intervals intersect must land
  in the same split. One transmission heard by four receivers is four files and
  one event, and recording-level splitting does not help because the unit of
  independence is the transmission. This is how `--group-by` gets verified
  rather than assumed.
- **The chance line, always.** `audit` and `stats` print the class distribution
  and what a constant predictor would score. Not a check and not a status —
  imbalance is a property of the input, and the chance line is the number that
  makes any accuracy figure readable.

### Grouping by SigMF collection

`--group-by` gains a third scheme, `collection`, which reads `core:collection`
from the Global Object. This is not a new mechanism — it is the field SigMF
already defines for relating recordings, and the specification's own example for
a Collection's `core:streams` is "channels from a phased array", i.e.
simultaneous multi-channel acquisition. That is precisely the case a
recording-level split cannot see.

```bash
iqforge build recordings/ -o ds/ --group-by collection
```

`iqforge audit` reports a matching `collection members` row: whether the members
of each declared collection landed in one split.

**It is a hint, not a proof, and the code says so.** A Collection asserts that
recordings are *related*; it does not assert that they are statistically
dependent and must not be separated. A collection holding "every recording in my
paper" and one holding "the four simultaneous receptions of one frame" are the
same object to anything reading the format, and only the second is a constraint.
So the audit row is capped at `PASS/sample` — it is never `PASS/proof`, however
clean the answer — and `did_not_check` states the limit explicitly. Grouping on
it is still safe, because holding independent recordings together costs split
flexibility and never correctness.

A second limit, worth knowing before relying on it: `core:collection` is a
single string, so a recording belongs to at most one collection. A dataset
needing nested levels — this transmission, within this session, within this
deployment — can record exactly one of them. See
[methodology §6](https://github.com/emrefbulut/iqforge/blob/main/docs/methodology.md)
for the full list of five limits and for why the argument for a SigMF extension
is about *meaning* rather than structure.

### Measurement

The leakage experiment was repeated on **LoRaIQ** — 312 recordings over 13
capture sessions, class = propagation environment, grouped by transmission id so
that the four rooftop receivers hearing one frame stay in one split. It is the
first assessed dataset `iqforge audit` returns `unknown` for, and the first with
the region of partial competence the measurement needs: the honest arm sits
around 65% against a 46% chance line.

| stride | overlap | recording-level | window-level | inflation (paired) | t |
|---|---|---|---|---|---|
| 1024 | 0% | 66.8% | 68.3% | **+1.5 pp** ± 1.7 | 0.9 |
| 768 | 25% | 67.8% | 67.3% | **−0.4 pp** ± 2.3 | −0.2 |
| 512 | 50% | 65.8% | 69.4% | **+3.7 pp** ± 2.3 | 1.6 |
| 256 | 75% | 69.2% | 68.8% | **−0.4 pp** ± 1.7 | −0.2 |
| 128 | 88% | 64.5% | 74.1% | **+9.6 pp** ± 2.7 | **3.5** |

15 seed pairs per row, 150 runs, CPU (`torch 2.13.0+cpu`).

**Established.** Overlap is the mechanism. At zero overlap the inflation is
indistinguishable from zero for the third time across three independent
datasets — synthetic **+0.2**, DASH7 **−3.7**, LoRaIQ **+1.5**. And at 7/8
overlap the effect is large and, for the first time on real data,
individually significant: **+9.6 pp, t = 3.5**. The DASH7 repeat could only
report a trend at t = 2.07.

**Not established.** The shape of the dose-response curve. The intermediate
points do not line up on any of the three datasets:

| overlap | synthetic | DASH7 | LoRaIQ |
|---|---|---|---|
| 0% | +0.2 | −3.7 | +1.5 |
| 25% | +0.5 | −3.4 | −0.4 |
| 50% | +11.5 | +4.3 | +3.7 |
| 75% | **+22.9** | **+8.7** | −0.4 |
| 88% | +13.4 | +7.7 | **+9.6** |

At n = 15 the per-pair spread (−11 to +14 pp at stride 256; −6 to +38 at 128)
resolves only the largest effect. The intermediate rows were **not** re-run with
more seeds: enlarging a sample after seeing the result lets the result choose
the stopping rule.

The direction was predicted in advance from the synthetic sweep, so this is a
confirmatory test rather than an exploratory one — five strides were measured
because the synthetic sweep measured five.

[`docs/methodology.md`](https://github.com/emrefbulut/iqforge/blob/main/docs/methodology.md)
gains three cases from this cycle: LoRaIQ as a fifth assessed dataset — the
first that publishes acquisition provenance, in a sidecar CSV under column names
its authors invented; a disqualification that belongs to a dataset *paired with
a class definition* rather than to the data, where the unit that must stay
together spans every class and no leak-free split exists; and an acquisition
method that was byte-correct per file and invalid in aggregate.

### Install

```bash
pip install --upgrade 'iqforge[torch]'
```

Python 3.11+. `torch` is optional; `info`, `inspect`, `build`, `stats` and
`audit` all work without it. Datasets built by `0.1.0`–`0.3.0` are still
readable — but see the correctness notice above before trusting one that was
labelled from a CSV.
